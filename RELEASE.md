## 2. Цели релиза

Передать в эксплуатацию решение для генерации тестовых данных PostgreSQL на основе статистики исходной БД. В релиз входят:

- **Приложение экспорта (`pg_ozerki`)** — расширение для PostgreSQL, выгружающее схему, статистику, индексы, ограничения и план запроса в файлы.
- **Приложение генерации (`datagen`)** — Java-утилита, восстанавливающая по этим файлам синтетическую БД, статистически близкую к исходной.
- **Туториал** — воспроизводимый кейс end-to-end (исходная БД → экспорт → генерация → сверка плана запроса).

### Что нового по сравнению с MVP

- Побатчевая генерация данных.
- Распараллеливание загрузки и генерации.

### Вне scope этого релиза

- Поддержка расширенной статистики
- Поддержка результатов выполнения explain analyze
- Поддержка СУБД, отличных от PostgreSQL.
- GUI / web-интерфейс.

## 3. Инструкция по развёртыванию

### 3.1 Предусловия

- PostgreSQL ≥ 15 с исходниками (для сборки приложения экспорта `pg_ozerki`).
- JDK 21+, Gradle wrapper включён в репозиторий.

### 3.2 Сборка

**Экспортёр:**

```bash
cp -r pg_ozerki <PG_SRC>/src/bin/
cd <PG_SRC>/src/bin/pg_ozerki
make install
```

**Генератор:**

```bash
cd datagen
./gradlew jar
# Артефакт: datagen/build/libs/datagen-1.0-SNAPSHOT.jar
```

### 3.3 Запуск (golden path)

См. `tutorial/README.md` — пошаговый сценарий с готовыми конфигами `export_config.yaml` / `datagen_config.yaml`.

### 3.4 Артефакты релиза

- `datagen-1.0-SNAPSHOT.jar` — fat JAR генератора.
- `pg_ozerki` — собранный бинарь расширения.
- `tutorial/` — папка с готовым кейсом использования.

## 5. Безопасность

> Раздел обязателен — выносим **в RELEASE.md**, не в SRS.

### 5.1 Модель угроз

**Ключевой риск инструмента — утечка чувствительных данных из исходной БД через файлы-артефакты экспорта.**

Артефакты, которые производит `pg_ozerki`, **по дизайну содержат фрагменты реальных данных**:

- `stats.csv`, колонка `mcv` — Most Common Values, **буквальные значения колонки** из `pg_stats`. Если экспортирована колонка `users.email` — MCV это реальные email-адреса. То же для `phone`, `passport`, `card_number`.
- `stats.csv`, колонка `hbounds` — границы гистограмм, **тоже реальные значения** колонки (например, реальные даты рождения по квантилям).
- `schema.sql` — `DEFAULT`-значения и `CHECK`-констрейнты могут содержать литералы с PII.
- `explain.json` — план запроса, если запрос был `WHERE email = 'ivanov@bank.ru'`, литерал попадёт в план.
- `query.sql` — текст опорного запроса; может содержать литералы.

Пользователь, не отдавая себе в этом отчёта, прогоняет утилиту на проде и потом отправляет `stats.csv` коллегам в Slack, прикладывает к Jira-тикету, коммитит в публичный репозиторий или передаёт подрядчику. **Утечка происходит не через канал передачи БД (его нет), а через канал передачи артефактов.**

### 5.2 Выявленные угрозы

| # | Угроза | Канал | Серьёзность |
|---|---|---|---|
| **T1** | Экспорт на проде → MCV содержит реальные PII (email, телефон, ФИО) → артефакт попадает к третьим лицам | `stats.csv` (`mcv`, `hbounds`) | **Critical** |
| **T2** | План запроса содержит литералы из `WHERE`/`VALUES` исходного запроса | `explain.json`, `query.sql` | **High** |
| **T3** | `DEFAULT` / `CHECK` в DDL экспортируются как есть; CHECK может ссылаться на конкретные ID/значения | `schema.sql`, `constraints.csv` | Medium |
| **T4** | Пользователь экспортирует БД с PII «на посмотреть», артефакты остаются в `~/Downloads`, `/tmp`, в логах CI без очистки | filesystem | Medium |
| **T5** | Пароль БД хранится в открытом виде в YAML-конфиге, попадает в `ps`, history, бэкап dotfiles | `*_config.yaml` | Medium |

### 5.3 План устранения

**Технические меры:**

- [ ] T1: добавить в `pg_ozerki` флаг `--mask-mcv <columns.yaml>` — список колонок, для которых MCV/hbounds **не экспортируются**, а заменяются на синтетику той же кардинальности.
- [ ] T1: по умолчанию **отказывать** в экспорте колонок с типами / именами, похожими на PII (email/phone/passport/inn/snils), если не передан явный флаг `--allow-pii`.
- [ ] T2: при экспорте `EXPLAIN` использовать `EXPLAIN (FORMAT JSON, COSTS FALSE, BUFFERS FALSE)` без `ANALYZE` и без литеральных значений (или маскировать литералы в плане перед записью).
- [ ] T3: при `--no-checks` дополнительно вырезать `DEFAULT`-выражения с литералами-строками длиной > 0.
- [ ] T5: убрать `password` из примеров YAML в README/туториале, заменить на чтение из `PGPASSWORD` / `.pgpass`.

**Документационные меры (важнее технических — без них пользователь сам себя подставит):**

- [ ] **Баннер в README** и при старте `pg_ozerki`: «Артефакты экспорта содержат фрагменты реальных данных колонок (MCV, histogram bounds). Не передавайте их за периметр, где допустимо хранение исходной БД.»
- [ ] В `tutorial/README.md` — отдельный раздел «Что НЕ делать»: не запускать на проде без `--mask-mcv`, не коммитить `*_stats.csv` в git, не прикреплять к публичным тикетам.
- [ ] В RELEASE.md / SAD — пометка о классификации артефактов: те же требования, что к исходной БД.

### 5.4 Эксплуатационные рекомендации

- **Артефакты экспорта классифицируются по тому же уровню чувствительности, что и исходная БД.** Если БД — «коммерческая тайна», то и `stats.csv` — коммерческая тайна.
- Запускать экспортёр под отдельной ролью PostgreSQL с правами только на нужные колонки (`GRANT SELECT (col1, col2) ON tbl`). Без прав на колонку — её статистика не попадёт в `pg_stats` для этой роли.
- Для боевого использования — экспортировать **на изолированной реплике** прод-БД, а не на самой проде.
- Перед передачей `stats.csv` за периметр — открыть и проверить глазами поля `mcv` и `hbounds` всех колонок.
- `datagen` запускать в изолированной сети, не публиковать порт целевого PostgreSQL наружу.
- `datagen` **перезаписывает** целевую БД — не направлять на прод.
